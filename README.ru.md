# Employee Task Management

[English](README.md) | **Русский**

REST API и двуязычный веб-клиент для назначения, отслеживания и обновления задач сотрудников. Сервис рассчитан на команды, которым нужен единый источник правды по задачам, ответственным и статусам — без полноценной системы управления проектами.

## Проблема

Руководителям нужен надёжный способ создавать работу, назначать её сотрудникам и видеть статус. Сотрудникам нужен простой способ понять, что на них назначено, и отчитаться о прогрессе. Часто это до сих пор живёт в чатах и таблицах, из-за чего сложно понять, кто отвечает за задачу и где она застряла.

## Решение

Проект даёт небольшой команде бэкенд для такого процесса — пользователи с JWT-аутентификацией, ролевой доступ и ресурс задачи со статусом, приоритетом, исполнителем и сроком — плюс веб-клиент, чтобы работать с этим процессом без инструментов для API. Клиенты могут фильтровать, искать и пагинировать задачи, а не загружать весь набор данных целиком.

## Основные возможности

- Регистрация и вход с access- и refresh-токенами
- Ролевой доступ: `ADMIN`, `MANAGER`, `EMPLOYEE`
- Создание, чтение, обновление и удаление задач с назначением исполнителя
- Статусы (`TODO`, `IN_PROGRESS`, `DONE`, `CANCELLED`) и приоритеты (`LOW`, `MEDIUM`, `HIGH`, `CRITICAL`)
- Пагинация, фильтрация, сортировка и поиск
- Необязательные подзадачи через `parent_id`
- Веб-клиент на русском и английском с переключением с любой страницы, светлая и тёмная темы
- Обзор с нагрузкой, просроченными задачами и разбивкой по статусам и приоритетам
- Миграции Alembic для PostgreSQL
- Автотесты и CI в GitHub Actions
- Docker Compose для локального запуска и деплоя на VPS

## Архитектура

```
Браузер (статический SPA, раздаётся по /)
  ↓  fetch + Bearer-токен
FastAPI (роутинг / валидация)
  ↓
Сервисный слой (бизнес-правила и авторизация)
  ↓
SQLAlchemy (асинхронный доступ к данным)
  ↓
PostgreSQL
```

HTTP-слой остаётся тонким. Сервисы решают, кто может создавать, смотреть, менять или удалять ресурс. CRUD-модули выполняют запросы к базе и подгружают связанные записи через `selectinload`, если ответ содержит вложенные коллекции.

## Аутентификация

Клиент регистрируется по email и паролю, затем вызывает `POST /auth/login` и получает JWT access-токен и непрозрачный refresh-токен.

- Пароли хешируются и никогда не хранятся в открытом виде
- Access-токен истекает (по умолчанию 30 минут)
- Refresh-токены хранятся как SHA-256 хеши, истекают (по умолчанию 7 дней) и ротируются при использовании
- `POST /auth/logout` отзывает refresh-токен
- Первый зарегистрированный пользователь получает роль `ADMIN`, чтобы можно было инициализировать новое окружение

Access-токен передаётся в заголовке `Authorization: Bearer <token>`.

## Роли и права

| Действие | ADMIN | MANAGER | EMPLOYEE |
| --- | --- | --- | --- |
| Управление пользователями и ролями | да | нет | нет |
| Список сотрудников в своей зоне | да | да | только своя запись |
| Создание и назначение задач | да | да | нет |
| Просмотр задач | все | все | только назначенные |
| Изменение полей задачи | да | да | только статус своих задач |
| Удаление задач | любые | только созданные собой | нет |

Зона менеджера: сотрудники, у которых `manager_id` указывает на этого менеджера, плюс сотрудники без назначенного менеджера.

## Веб-клиент

API раздаёт веб-клиент по корневому адресу. Запустите приложение и откройте http://127.0.0.1:8000 — отдельная сборка, dev-сервер и запись в `CORS_ORIGINS` не нужны, потому что клиент отдаётся с того же origin, что и API.

Что умеет:

- Регистрация и вход; сессия продлевается автоматически, когда истекает access-токен
- Обзор: всего / в работе / просрочено / выполнено, распределение по статусам и приоритетам, задачи, которые требуют внимания, и недавно созданные
- Список задач с поиском, фильтрами по статусу, приоритету и исполнителю, сортировкой, пагинацией и счётчиками по статусам
- Создание, редактирование, назначение и удаление задач, а также карточка задачи с полным описанием и метаданными
- Смена статуса прямо в списке, чтобы сотрудник мог отчитаться о прогрессе без открытия формы
- Справочник сотрудников с их задачами и админский экран для ролей, руководителей и состояния аккаунтов
- Страница профиля для смены своего email или пароля

Маршруты построены на хеше: `#/dashboard`, `#/tasks`, `#/tasks/:id`, `#/employees`, `#/users` (администраторы), `#/profile`. Интерфейс скрывает то, что роли недоступно, а API всё равно проверяет каждое правило самостоятельно.

На широком экране — боковое меню и таблицы. На планшете — узкая иконная рейка. На телефоне — выдвижное меню, вертикальная вёрстка и карточки задач вместо таблицы из семи колонок.

### Языки и оформление

Русский и английский равноправны. Переключатель находится в шапке на каждой странице, включая экраны входа и регистрации. Выбор сохраняется в браузере, подставляется в `<html lang>` и используется для форматирования дат и чисел; при первом визите берётся предпочитаемый язык браузера. Сообщения об ошибках от API тоже переводятся.

Рядом с переключателем языка находится переключатель светлой и тёмной темы: до первого изменения он следует настройке операционной системы.

### Реализация

`frontend/` — это обычные ES-модули без сборки и runtime-зависимостей, поэтому `docker compose up` раздаёт клиент без дополнительных шагов. `package.json` только помечает исходники как ESM и запускает тесты клиента. Роутинг построен на хеше (`#/tasks/12`), поэтому для работы прямых ссылок достаточно отдавать `index.html` по `/` без правил переписывания URL.

```
frontend/
  index.html             # Оболочка приложения
  css/styles.css         # Дизайн-токены и компоненты
  js/
    app.js               # Маршруты, проверки доступа, жизненный цикл сессии
    core/                # Клиент API, токены, i18n, права, фильтры
    layout/              # Боковое меню, шапка, мобильный drawer
    ui/                  # Кнопки, формы, таблицы, тосты, пустые и ошибочные состояния
    views/               # Обзор, вход, задачи, сотрудники, пользователи, профиль
  tests/                 # Набор тестов Node (`npm test`)
```

Токены хранятся в `localStorage`: это удобно для клиента на том же origin, но доступно любому скрипту на странице. Если вы добавите сторонние скрипты, сначала переходите на сессии в cookie.

Доступность закладывалась сразу, а не дописывалась потом: подписанные поля с сообщениями валидации, ссылка перехода к содержимому, диалоги с ловушкой фокуса и закрытием по Escape, `aria-current` на активном пункте меню, тосты в live-region и видимые focus-рамки. Вёрстка и анимации учитывают `prefers-reduced-motion`.

## Документация API

После запуска API документация OpenAPI доступна по адресам:

- Swagger UI: http://127.0.0.1:8000/docs
- ReDoc: http://127.0.0.1:8000/redoc

В Swagger авторизуйтесь access-токеном из `POST /auth/login`.

## Локальный запуск

Нужны Python 3.12, Poetry и PostgreSQL (или Docker).

```bash
cp .env.example .env
# укажите JWT_SECRET и параметры базы в .env

poetry install
alembic upgrade head
poetry run uvicorn src.app:app --reload --host 0.0.0.0 --port 8000
```

Затем откройте http://127.0.0.1:8000 — это веб-клиент, а http://127.0.0.1:8000/docs — документация API. Первый зарегистрированный аккаунт становится администратором.

## Переменные окружения

Скопируйте `.env.example` в `.env`. В репозитории нет настоящих секретов.

| Переменная | Назначение |
| --- | --- |
| `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME` | Подключение к PostgreSQL |
| `DB_ECHO` | Логировать SQL, если `true` |
| `JWT_SECRET` | Ключ подписи access-токенов |
| `JWT_ALGORITHM` | Алгоритм JWT (по умолчанию `HS256`) |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Время жизни access-токена |
| `REFRESH_TOKEN_EXPIRE_DAYS` | Время жизни refresh-токена |
| `CORS_ORIGINS` | Необязательный список origin'ов через запятую; для встроенного клиента не нужен |
| `DEBUG` | Подробные логи приложения, если `true` |

## Запуск тестов

Тесты используют изолированную in-memory SQLite и не требуют PostgreSQL.

```bash
poetry install --with dev
poetry run pytest
```

```bash
poetry run ruff check src tests
```

У веб-клиента свой набор тестов (словари, права, фильтры, сроки, метрики, разбор ошибок API). Нужен Node.js 22+, дополнительные пакеты не требуются:

```bash
npm test
```

## Тестирование

Набор покрывает регистрацию и вход, неверные учётные данные, истечение токена, ротацию refresh-токена, ограничения по ролям, CRUD и назначение задач, фильтрацию, пагинацию, сортировку, а также нарушения ограничений: дублирующий email и удаление пользователя, у которого ещё есть созданные задачи. Отдельные тесты проверяют, что веб-клиент раздаётся и что статика не перекрывает маршруты API. `npm test` проверяет словари клиента, правила ролей, фильтры задач, логику сроков и разбор ошибок API.

## CI

GitHub Actions запускается на каждый push и pull request: установка зависимостей, линтинг Ruff, Pytest, тесты веб-клиента (`npm test`) и сборка Docker-образа. Джоба падает, если падают тесты.

## Деплой

Предполагаемый продакшен-путь:

```
GitHub → Docker-образ → VPS → Nginx → HTTPS → FastAPI → PostgreSQL
```

Практические замечания:

- Секреты храните в окружении сервера или в менеджере секретов, не в git
- Перед приёмом трафика выполняйте `alembic upgrade head` (entrypoint образа делает это сам)
- Поставьте Nginx перед Uvicorn и завершайте TLS там; пример есть в `deploy/nginx.example.conf`
- Не открывайте PostgreSQL наружу на VPS
- Укажите `DEBUG=false` и длинный случайный `JWT_SECRET`
- В репозитории нет облачного деплой-воркфлоу; выкат на VPS — это `docker compose pull/up` (или аналог) на хосте

## Реализованные меры безопасности

- Хеширование паролей через fastapi-users / pwdlib
- JWT access-токены со сроком жизни
- Refresh-токены хешируются при хранении и ротируются
- Проверка ролей в сервисном слое, а не только в роутере
- Регистрация не принимает `is_superuser` и роль от клиента
- Учётные данные БД и JWT-секрет берутся из окружения
- Ответы API не содержат стектрейсы, SQL и секреты
- Docker-образ работает от непривилегированного пользователя
- CORS выключен, пока явно не задан `CORS_ORIGINS`; встроенному клиенту исключение не нужно, он работает с того же origin
- Веб-клиент скрывает действия, недоступные роли, но авторизацию обеспечивает сервисный слой, а не интерфейс
- Известный компромисс: клиент хранит токены в `localStorage`, доступном любому скрипту на странице

Это не означает, что сервис «безопасен» для любой модели угроз. Перед продакшеном отдельно проверьте работу с секретами, TLS и сетевой доступ.
